# Техническое задание на улучшение веб-приложения многопользовательской игры «Мемомариум»

## 1. Основание, цели и границы работ

Настоящее ТЗ составлено на основании анализа пользовательского архива `/mnt/data/src.rar`. В архиве находится frontend-приложение на Vue 3 + TypeScript с тремя пользовательскими контурами: панель ведущего `/host`, мобильный интерфейс участника `/play/:roomCode` и общий экран `/screen`, `/screen/:roomCode`. В исходниках присутствуют Pinia-store, Vue Router, HTTP-клиент, WebSocket-клиент, компоненты игрового состояния и тесты. Backend, конфигурация сборки и полный набор статических ресурсов в архиве отсутствуют, поэтому требования ниже не должны трактоваться как изменение серверного контракта без отдельной проверки backend.

Цель работ — повысить надёжность синхронизации, устранить подтверждённые дефекты frontend, переработать визуальную систему приложения и превратить интерфейс из нейтрального административного UI в выразительную party-game-среду, при этом не ухудшив работу на смартфонах, слабых мобильных устройствах и нестабильных сетях.

Требования разделяются на три интерфейса.

| Интерфейс | Основная среда | Главный приоритет |
|---|---|---|
| `/play/:roomCode` | браузер смартфона, portrait и landscape | скорость действий, крупные touch-targets, читаемость, отсутствие случайных действий |
| `/host` | ноутбук/планшет ведущего | контроль комнаты, диагностика, управление контентом и настройками |
| `/screen`, `/screen/:roomCode` | ТВ, проектор, большой монитор | шоу-подача, крупная типографика, анимация фаз, аудио, видимость с расстояния |

Для доступности интерфейс должен ориентироваться как минимум на WCAG 2.2 AA. WCAG 2.2 требует минимальную область указателя 24×24 CSS px для критерия 2.5.8; для данного продукта устанавливается более строгий внутренний минимум 44×44 CSS px для основных интерактивных элементов на смартфоне, что соответствует enhanced-критерию WCAG 44×44. citeturn276182search0turn499722view1 Текст должен иметь контраст не ниже 4.5:1 для обычного текста и 3:1 для крупного. citeturn742651search1turn742651search18

### Допущения и ограничения

Архив не содержит backend-кода, поэтому следующие сведения должны быть подтверждены перед изменением контрактов: допустимость исключения host-player, серверная гарантия монотонности `revision`, наличие серверного времени или time-offset для синхронного аудио, формат WebSocket сообщений сверх `SNAPSHOT` и `STATE_UPDATED`, правила хранения пользовательских настроек звука и анимаций.

В архиве не обнаружены `package.json` и конфигурация bundler. Поэтому создание `public/audio/` и импорт статических ассетов в этом ТЗ являются целевой структурой; фактический способ упаковки должен быть адаптирован под используемый bundler.

Screen Wake Lock API доступен только в secure context, а браузер может снять блокировку при потере видимости документа или переходе устройства в режим энергосбережения; MDN рекомендует повторно запрашивать lock после возврата документа в активное состояние. citeturn742651search0turn742651search14 Это должно быть учтено в улучшенной реализации.

## 4. Требования к надёжности состояния и соединения

### WebSocket lifecycle

Текущая реализация `GameSocket.connect()` безусловно вызывает `open()` и не закрывает уже существующий `WebSocket`. Это подтверждено в `src/services/gameSocket.ts`: `connect()` меняет `roomCode`, сбрасывает `reconnectAttempt` и вызывает `open()`, а `open()` заменяет поле `this.ws` новым экземпляром.

Требуется изменить lifecycle следующим образом:

| Требование | Реализация |
|---|---|
| повторный `connect()` к тому же endpoint | если сокет `OPEN`/`CONNECTING`, не создавать второй |
| переход в другую комнату | отменить reconnect timer, закрыть предыдущий socket, создать новый |
| смена `screen` режима | считать новым endpoint и переподключить |
| callback старого socket | игнорировать, если socket уже не является текущим |
| reconnect timer | не более одного активного timer |
| `close()` | гарантированно отключает reconnect |
| onclose старого socket | не может запускать reconnect для новой комнаты |

Рекомендуемая реализация: локально сохранять `const socket = new WebSocket(url)` и в каждом handler проверять `if (socket !== this.ws) return`; дополнительно использовать `connectionGeneration` или monotonically increasing connection id. Простого вызова `this.ws?.close()` перед новым socket недостаточно, потому что `onclose` старого socket может сработать уже после сброса глобального `closedByUser`.

WebSocket API предоставляет двустороннее постоянное соединение, а явное закрытие неиспользуемого соединения является рекомендуемой практикой. citeturn742651search20turn742651search37

### Monotonic revision

`src/stores/gameSession.ts` сейчас принимает любой snapshot через:

`setSnapshot(snap) -> snapshot = snap; revision = snap.revision`.

Это допускает race:

1. приходит `STATE_UPDATED revision=105`;
2. запускается `resync()`;
3. приходит более новый `STATE_UPDATED revision=106`;
4. второй `resync()` отвечает первым;
5. затем первый HTTP-запрос возвращает snapshot 105;
6. `setSnapshot()` перезаписывает актуальное состояние.

Требуется:

```ts
function setSnapshot(snap: GameSnapshot): boolean {
  if (
    snapshot.value &&
    snap.room.code === snapshot.value.room.code &&
    snap.revision < revision.value
  ) {
    return false
  }

  snapshot.value = snap
  revision.value = snap.revision
  return true
}
```

Дополнительно `resync()` должен использовать request sequence:

```ts
let resyncSeq = 0

async function resync(screen = false) {
  const roomCode = currentRoomCode.value
  if (!roomCode) return

  const seq = ++resyncSeq
  const snap = await apiClient.getState(roomCode, screen)

  if (seq !== resyncSeq) return
  if (roomCode !== currentRoomCode.value) return

  setSnapshot(snap)
}
```

Если backend допускает одинаковые `revision` с различным payload, это необходимо подтвердить. По умолчанию ТЗ предполагает, что `revision` монотонен в пределах одной комнаты.

### Reconnect UX

При `connecting` и `reconnecting` игровые controls, отправляющие команды, должны блокироваться, если действие может породить дублирующий запрос. Статический просмотр snapshot разрешается.

На мобильном экране показывать компактный non-modal banner:

`Связь потеряна. Восстанавливаем…`

После восстановления:

`Связь восстановлена` на 1.5–2 секунды.

Нельзя очищать выбранный мем или ввод ситуации только из-за временного reconnect. Состояние локальной формы очищается только при смене фазы, подтверждённом сервером submit или `sessionLost`.

### DEF-02: точное исправление `scoreConfig`

Сейчас:

```ts
const form = reactive<GameSettingsDTO>({ ...props.settings })
```

Требуется:

```ts
function cloneSettings(s: GameSettingsDTO): GameSettingsDTO {
  return {
    ...s,
    scoreConfig: { ...s.scoreConfig },
  }
}

const form = reactive<GameSettingsDTO>(cloneSettings(props.settings))

watch(
  () => props.settings,
  (s) => Object.assign(form, cloneSettings(s)),
)
```

На save:

```ts
emit('save', cloneSettings(form))
```

**Acceptance:** изменение `form.scoreConfig.partialGuesser` до нажатия «Сохранить» не меняет `props.settings.scoreConfig.partialGuesser`.

### DEF-04: `/screen`

Предыдущую формулировку «маршрут `/screen` отсутствует» считать неверной. Маршрут присутствует в `src/router/index.ts`. Реальная проблема: route без параметра вычисляет:

```ts
route.params.roomCode ?? session.currentRoomCode ?? ''
```

и в `onMounted` подключение происходит только при truthy roomCode.

Требуемое поведение `/screen`:

- если `currentRoomCode` известен — redirect `/screen/:roomCode`;
- если неизвестен — показать экран выбора комнаты или поле room-code;
- пустой экран без объяснения запрещён;
- неверный код комнаты — error-state с кнопкой возврата;
- после выбора использовать `router.replace({ name: 'screen-room', params: { roomCode }})`.

### DEF-05: Host / PlayerList

Текущий `PlayerList` скрывает kick только для `currentPlayerId`. Поэтому передача `hostPlayerId` не влияет на кнопку. До изменения backend необходимо подтвердить, может ли администратор исключать host-player.

Если host запрещено исключать, условие должно стать:

```vue
v-if="
  showKick &&
  player.id !== currentPlayerId &&
  player.id !== hostPlayerId
"
```

Для большей расширяемости рекомендуется заменить на:

```ts
protectedPlayerIds?: string[]
```

## 6. Требования к мобильному UI, ведущему и общему экрану

### Смартфон игрока `/play/:roomCode`

Минимальная поддерживаемая логическая ширина layout: 320 CSS px; целевой диапазон 360–430 px.

Основная структура:

```text
safe-area top
header: room / connection / sound
phase title
main content
sticky action area
safe-area bottom
```

Нижняя action-area:

```css
padding-bottom: calc(12px + env(safe-area-inset-bottom));
```

`env(safe-area-inset-*)` предназначены для размещения UI вне областей, которые могут перекрываться вырезами, закруглениями и browser UI. citeturn276182search5

Требования:

| Элемент | Требование |
|---|---|
| primary CTA | min-height 52 px, width 100% |
| secondary button | min 44×44 px |
| meme card | tap по всей карточке |
| selected meme | border + scale ≤1.02 + check icon; цвет не единственный indicator |
| submit | sticky снизу, не перекрывает content |
| disabled | визуально distinct + `disabled` attribute |
| vote grid | 2 columns на ≤480 px; при landscape допускается 3 |
| text input | font-size не менее 16 px |
| error | рядом с контекстом + `role=alert` для критических ошибок |
| connection banner | non-modal |

Все функции, реализуемые swipe, должны иметь доступную альтернативу через tap/button. WCAG 2.2 требует, чтобы path-based pointer gesture имел single-pointer alternative, если gesture не является обязательным. citeturn499722view1

### Панель ведущего `/host`

Host UI не обязан быть mobile-first, но должен корректно работать от 768 px и иметь приемлемый fallback от 360 px.

Переработать layout:

- верхняя status bar: Room, Phase, WebSocket, Sound, Fullscreen Screen link;
- две колонки на ≥1024 px: слева Players/Game Controls, справа Room/QR;
- Settings и Content — tabs или accordion;
- destructive actions визуально отделить;
- текущая фаза — цветной chip;
- кнопка FORCE_RESOLVE_PHASE обязательно с confirmation;
- при connection loss game commands disabled;
- room code и QR остаются видимыми без прокрутки на desktop.

### Общий экран `/screen/:roomCode`

Screen UI проектируется для 16:9, но должен работать на 4:3 и ultrawide.

Контент не должен быть просто увеличенной desktop-карточкой. На каждой фазе использовать отдельную композицию:

| Фаза | Presentation |
|---|---|
| LOBBY | крупный room code, QR/URL, аватары игроков |
| PREPARATION | full-width progress + count |
| ROUND_SELECTION | ситуация в центре + active player |
| ROUND_VOTING | ситуация сверху, мемы крупной сеткой |

Размеры должны использовать `clamp()` и viewport units вместо фиксированных только Tailwind text classes.

## 7. Улучшение интерфейса, анимаций и звукового сопровождения

### Визуальная концепция

Целевой стиль: энергичная party-game эстетика без визуального шума. Фон преимущественно тёмный, но важные события получают яркий purple/cyan/yellow accent. Серый допускается только как secondary neutral.

В `src/style.css` определить semantic CSS variables и базовые utility classes. Компоненты `AppButton.vue` и `AppCard.vue` перевести на variants.

`AppButton`:

```ts
variant:
'primary' | 'secondary' | 'ghost' | 'danger' | 'success'
```

`AppCard`:

```ts
variant:
'default' | 'game' | 'highlight' | 'transparent'
```

### Анимационная система

Все анимации должны быть event-driven и не должны блокировать gameplay.

| Событие | Эффект | Длительность |
|---|---|---:|
| вход в фазу | fade + translate 8–16 px | 200–300 ms |
| выбор meme | scale 1 → 1.02 + ring | 120–180 ms |
| submit success | check pop | 250 ms |
| таймер ≤10 s | warning pulse | 700–900 ms loop |
| таймер ≤5 s | stronger pulse | 450–600 ms |
| начало voting | cards stagger | 30–60 ms/card |
| reveal | flip/fade sequential | 250–400 ms/card |
| leaderboard update | FLIP-style reorder | 300–450 ms |
| winner | confetti | 3–5 s |
| connection restored | subtle toast | 180 ms |

Не использовать постоянные декоративные motion loops на мобильном PlayerView, кроме таймера.

Создать `useReducedMotion.ts`, основанный на:

```ts
window.matchMedia('(prefers-reduced-motion: reduce)')
```

`prefers-reduced-motion` поддерживается для определения системного предпочтения уменьшить несущественную анимацию. citeturn276182search4

При reduce:

- отключить confetti;
- убрать stagger;
- transform animations заменить на opacity ≤120 ms;
- не пульсировать whole-screen;
- timer warning — статическая смена цвета;
- сохранять функциональную обратную связь.

WCAG также предусматривает возможность отключения motion animation, вызванной взаимодействием, когда она не является существенной. citeturn499722view1

### Autoplay и разблокировка

Нельзя рассчитывать на автоматическое воспроизведение звука при загрузке страницы. Браузеры обычно блокируют audible autoplay, если пользователь ещё не взаимодействовал со страницей; это касается и `HTMLMediaElement.play()`, и Web Audio. citeturn276182search2turn276182search3

Требуется:

- `/play`: вызывать `audioManager.unlock()` в user gesture при «Присоединиться»;
- `/host`: unlock при первом клике по странице или через явную кнопку;
- `/screen`: при открытии показывать ненавязчивую кнопку `Включить звук`; нажатие Fullscreen также может инициировать unlock;
- если `play()` rejected — не считать это ошибкой игры;
- показывать muted icon;
- повторный unlock после первого успешного не требуется.

Запрещено искусственно генерировать скрытый click.

| Событие | Player | Host | Screen |
|---|---|---|---|
| join success | short success | optional | player joined soft cue |
| phase PREPARATION | phase cue | phase cue | prominent cue |

### Dedupe аудиособытий

Ключ:

```text
roomCode:revision:event
```

Пример:

```text
ABCD:143:PHASE_ROUND_VOTING
```

Audio cue не воспроизводится повторно для уже обработанного dedupe key.

При первой загрузке snapshot:

- не воспроизводить «phase change» как историческое событие;
- можно начать looped background music после unlock;
- countdown ticks включаются только с текущего следующего порога.

### Таймер и синхронизация

Последние 5 секунд определять по:

```ts
remainingMs = Date.parse(phaseDeadlineAt) - Date.now()
```

Tick воспроизводить при переходе через целые секунды 5,4,3,2,1, а не через независимый `setInterval(1000)`.

Точное синхронное звучание на нескольких устройствах нельзя гарантировать только по текущему frontend, потому что в архиве не найден server-clock offset. Для синхронизации точнее ±100–200 ms backend должен передавать server time или clock offset. До этого аудио на разных устройствах считать best-effort.

### Аудиоформаты

Минимальный комплект ассетов должен поставляться в MP3. При необходимости Safari/Firefox совместимости можно добавить второй format, но обязательное runtime transcoding не требуется.

AudioManager обязан обработать:

- failed load;
- 404;
- decode error;
- promise rejection `play()`;
- mute;
- tab background;
- быстрые phase changes;
- multiple simultaneous cues.

Фатальная ошибка аудио не может блокировать игру.

### Definition of Done

Задача считается завершённой только когда выполнены все условия:

1. Все P0/P1 пункты реализованы и покрыты тестами.
2. Не создаются параллельные WebSocket при повторном `connect()`.
3. Snapshot не может откатить revision назад внутри комнаты.
4. `SettingsForm` не мутирует props через `scoreConfig`.
5. `/screen` без code имеет определённое UX-поведение.
6. Player UI проходит проверку на 320 px и safe-area devices.
7. Touch controls соответствуют внутреннему минимуму 44×44 px.
8. Основной текст проходит контраст WCAG AA.
9. `prefers-reduced-motion` соблюдается.
10. Audio работает после user gesture и корректно переживает autoplay rejection.
11. Ошибка аудио никогда не останавливает игру.
12. Phase cue не дублируется после reconnect/resync.
13. Screen получает отдельную show-oriented композицию для всех фаз.
14. Regression tests существующей игровой логики проходят.
15. Browser matrix пройдена без blocker/critical дефектов.
16. Показатели LCP/INP/CLS не ухудшены выше заданных порогов.
17. Все новые пользовательские настройки имеют устойчивые defaults и корректно восстанавливаются после повреждённого localStorage.
18. Изменения backend-контрактов отсутствуют либо отдельно согласованы и задокументированы.

Финальная реализация должна сохранить текущую модель игры и API, но изменить качество восприятия приложения: мобильный клиент — быстрый и тактильно понятный, host — управляемый и диагностируемый, общий экран — яркий, динамичный и пригодный для роли центрального экрана party-game.

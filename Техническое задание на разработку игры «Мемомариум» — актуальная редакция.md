# 2. Описание продукта

«Мемомариум» — локальная многопользовательская party-game по мотивам механики «Имаджинариума».

Вместо игровых карточек используются мемы.

Один компьютер выполняет одновременно роли:

- локального сервера;
- административной панели;
- источника общего игрового экрана.

Игроки подключаются к компьютеру со смартфонов через локальную Wi-Fi сеть.

Для подключения используется QR-код.

Интернет для проведения игры не требуется.

# 3. Основной пользовательский сценарий

1. Пользователь запускает `Memomarium.exe`.
2. Приложение запускает локальный сервер.
3. Выполняются миграции SQLite.
4. Определяется доступный LAN IP.
5. В браузере автоматически открывается `/host`.
6. Создаётся комната.
7. Генерируется QR-код.
8. Игроки сканируют QR.
9. Каждый вводит имя.
10. Первый подключившийся игрок становится `HOST`.
11. Игроки появляются в Lobby.
12. HOST настраивает игру.
13. HOST нажимает `Начать игру`.
14. Все игроки проходят Preparation.
15. Далее каждый игрок один раз становится Active Player.
16. Для его ситуации остальные выбирают мемы.
17. Проводится голосование.
18. Начисляются очки.
19. Показываются результаты.
20. HOST запускает следующий раунд.
21. После полного круга:
   - игра завершается;
   - либо начинается новый цикл при Infinite Mode.

# 4. Термины

## 4.1. Room

Комната, объединяющая подключённых игроков и настройки.

## 4.2. Local Admin

Системный административный пользователь, представляющий `/host` на компьютере.

Local Admin:

- не является игроком;
- не участвует в игре;
- имеет административные права.

## 4.3. HOST

Первый подключившийся Player.

HOST является обычным участником игры, но дополнительно имеет права:

- начать игру;
- перейти к следующему раунду;
- начать следующий цикл;
- выполнять разрешённые игровые административные команды.

## 4.4. Player

Участник игры.

## 4.5. Game

Запущенная партия.

## 4.6. GameCycle

Полный игровой круг.

В одном Cycle каждый участвующий игрок должен один раз стать Active Player.

## 4.7. Round

Раунд одного Active Player.

## 4.8. Active Player

Игрок, чья ситуация используется в текущем Round.

## 4.9. PreparedTurn

Подготовленная игроком пара:

- ситуация;
- оригинальный мем.

## 4.10. Original Meme

Мем, выбранный Active Player во время Preparation.

Это правильный вариант текущего раунда.

## 4.11. Submitted Meme

Мем, выбранный другим игроком для ситуации Active Player.

## 4.12. Hand

Набор мемов, из которого игрок выбирает один.

По умолчанию:

```text
handSize = 5
```

Использовать:

```text
Modular Monolith
```

- HTTP;

# 8. Главные архитектурные принципы

Обязательные правила:

1. Backend является единственным источником истины.
2. Frontend не реализует бизнес-логику игры.
3. Game Engine не зависит от HTTP.
4. Game Engine не зависит от WebSocket.
5. Game Engine не зависит от SQLite.
6. Game Engine не зависит от Vue.
7. Все state-changing операции выполняются через команды.
8. Каждая команда идемпотентна.
9. Каждое изменение состояния увеличивает `revision`.
10. Таймеры сохраняются как deadline, а не только как in-memory timer.
11. Игровой процесс должен восстанавливаться после restart приложения.
12. Скрытая игровая информация никогда не отправляется клиенту, которому она не предназначена.
13. Disconnect не равен Leave.
14. Состояние пользователя после reconnect определяется сервером.
15. Одна комната одновременно выполняет state-changing команды последовательно.

# 9. Сериализация команд комнаты

SQLite имеет одного основного writer, а сама игра содержит множество конкурентных действий.

Поэтому state-changing команды одной комнаты должны сериализоваться.

Рекомендуемая архитектура:

```text
HTTP / WS Command
       ↓
RoomCoordinator
       ↓
Room command lock / queue
       ↓
Transaction
       ↓
Game Engine
       ↓
Persistence
       ↓
Commit
       ↓
WebSocket notification
```

Не допускается параллельное изменение одного Room/Game несколькими goroutine без координации.

Можно использовать:

- per-room mutex;
- per-room actor;
- command queue.

Предпочтение — простая per-room сериализация.

# 17. Security boundary `/host`

`/host` представляет Local Admin.

Административная сессия должна создаваться только при открытии `/host` локально с компьютера, на котором работает сервер.

Удалённый LAN-клиент не должен автоматически получать Local Admin права только потому, что открыл `/host`.

Допускается:

- local admin token;
- loopback bootstrap;
- локальная admin cookie.

Tech Lead обязан реализовать механизм, исключающий простой удалённый доступ к административным командам.

# 18. `/screen`

- менять настройки;

- выполнять Next;

HOST не меняется при обычном Disconnect.

- игрок явно вышел;
- игрок был Kick;
- его участие окончательно завершено.

Новый HOST:

```text

```

# 33. Поведение Leave во время игры

Правила фиксируются следующим образом.

## До Game Start

Игрок полностью удаляется из текущего состава Room.

## GAME_PREPARATION

Игрок исключается из текущего Game.

Ожидание остальных пересчитывается.

## ROUND_SELECTION — не Active Player

Игрок исключается из обязательных submissions.

Если submission уже был сделан, он удаляется из текущего раунда.

## ROUND_SELECTION — Active Player

Текущий Round отменяется.

Игра переходит к следующему допустимому Active Player.

## ROUND_VOTING

Если voting уже сформирован:

- его Submitted Meme остаётся в ballot;
- уже полученные голоса остаются;
- его обязанность проголосовать снимается;
- его очки за текущий завершившийся Round могут быть начислены;
- дальнейшие раунды игрока пропускаются.

Это необходимо, чтобы не менять номера вариантов во время уже начавшегося голосования.

## ROUND_RESULTS

Результат текущего Round сохраняется.

Следующие раунды игрока пропускаются.

# 34. No-timer deadlock protection

Если таймер этапа равен `0`, игра потенциально может зависнуть из-за отсутствующего игрока.

Поэтому Local Admin и HOST должны иметь команду:

```text
FORCE_RESOLVE_PHASE
```

Она применяет к неготовым игрокам те же правила, что timeout.

Например:

Preparation:

```text
random situation + random meme
```

Round Selection:

```text
random meme
```

Voting:

```text
SKIPPED
```

# 53. Preparation dealing

В рамках Preparation руки игроков должны по возможности быть непересекающимися.

Это гарантирует уникальность Original Meme каждого игрока.

---

# 54. Минимальный объём мемов для запуска

При `N` игроках и `H = handSize` для Preparation требуется минимум:

```text
N × H
```

уникальных enabled мемов.

Для Round Selection потребуется исключить Prepared Originals.

Чтобы гарантировать непересекающиеся hands неактивных игроков:

```text
N + (N - 1) × H
```

enabled мемов.

Итоговое минимальное требование:

```text
requiredMemes =
max(
    N × H,
    N + (N - 1) × H
)
```

При недостатке контента START_GAME запрещён.

HOST получает понятную ошибку:

```text
Для 8 игроков с рукой 5 требуется минимум 43 активных мема.
Доступно: 32.
```

# 88. Transaction boundary

State-changing command должен выполняться атомарно:

```text
acquire room command lock
↓
BEGIN transaction
↓
check commandId
↓
load aggregate
↓
check revision
↓
validate authorization
↓
GameEngine.Handle
↓
persist new state
↓
persist command result
↓
increment revision
↓
COMMIT
↓
release lock
↓
broadcast
```

WebSocket message запрещено отправлять до успешного commit.

# 147. Critical invariants

Следующие условия не должны нарушаться ни при каких пользовательских действиях.

1. Один Player не может иметь два голоса в Round.
2. Один Player не может иметь два submissions в Round.
3. Один Player не может иметь два PreparedTurn в одном Cycle.
4. Active Player не голосует.
5. Player не голосует за свой Submitted Meme.
6. Original Meme не раскрывается до Results.
7. Owner VoteOption не раскрывается до Results.
8. Score изменяет только ScoreCalculator.
9. Room revision только увеличивается.
10. Один commandId выполняется максимум один раз.
11. Game Settings неизменяемы после Game Start.
12. Disconnect не удаляет Player.
13. Leave отзывает session.
14. После DB commit state должен быть восстанавливаемым.
15. WebSocket не может содержать state, который не был committed.
16. Client не может самостоятельно перейти GamePhase.
17. Секретные поля не должны существовать в неправильном projection.
18. Номера VoteOption не меняются после начала Voting.
19. После начала Voting Leave игрока не изменяет уже опубликованную ballot.
20. Любая Phase должна иметь способ завершиться через игроков, timeout либо FORCE_RESOLVE_PHASE.

# 151. Главная директива Tech Lead

При выборе между:

```text
сложной универсальной архитектурой
```

и:

```text
простой архитектурой, надёжно решающей требования V1
```

необходимо выбирать второй вариант.

Основная цель:

**локальная игра, которая стабильно работает на одном компьютере и нескольких телефонах, легко запускается, восстанавливается после сетевых проблем и не допускает рассинхронизации игрового состояния.**

Сложность должна добавляться только тогда, когда она устраняет конкретный риск или реализует явно указанное требование.
